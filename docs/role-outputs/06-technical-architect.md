## Q1.3: Pattern Matching Scope (Combinations & Multiple Systems)

**Recommended answer:** Support multiple patterns per diagram in Phase 1. Render as a single combined report (union of risk mappings). Split-view comparison is Phase 2.

**Rationale:**
- Real architectures combine patterns. A "Supervisor-Worker with Reflection Loops" is common. Forcing single-pattern output would reduce accuracy and frustrate users.
- The existing evaluator already handles a single archetype → multiple ASI risks → multiple NIST controls. Extending to multiple archetypes → union of ASI risks is architecturally simple.
- The existing `ScenarioComparison.tsx` component already supports side-by-side comparison. Phase 2 can reuse this for "Pattern A alone vs. Pattern A+B combined."

**Integration architecture:**
```
Diagram → LLM → [pattern_a (0.92), pattern_b (0.78)] 
                         ↓
         Pattern Evaluator (new file)
                         ↓
         For each pattern: look up ASI relevance weights
                         ↓
         Aggregate: union of ASI risks, max(weight) per ASI
                         ↓
         Generate heatmap cells using same CellState logic
                         ↓
         Render in existing ScenarioSimulator UI
```

**Multiple systems (separate diagrams):**
- Phase 1: One diagram at a time. Each analysis is independent.
- Phase 2: "Compare two architectures" — upload two diagrams, get side-by-side reports.
- This reuses the existing `ScenarioComparison` component with minimal changes.

**Confidence:** 0.85

## Q8.4: Scope Creep Prevention (Architectural Boundaries)

**Recommended answer:** Define a strict interface contract between the diagram analyzer and the existing system. The analyzer produces a `ScenarioResult`. Nothing else crosses the boundary.

**Architectural boundary diagram:**
```
┌─────────────────────────────────────────────────────────────┐
│ DIAGRAM ANALYZER SUBSYSTEM (new code)                       │
│                                                             │
│  DiagramAnalyzer.tsx (sidebar UI)                           │
│  diagram-analyzer.ts (LLM integration)                     │
│  pattern-evaluator.ts (pattern → ScenarioResult)           │
│  agentic-patterns.ts (pattern definitions)                 │
│                                                             │
│  OUTPUT: ScenarioResult (same type as scrambler)            │
├─────────────────────────────────────────────────────────────┤
│ BOUNDARY: Only ScenarioResult crosses this line             │
├─────────────────────────────────────────────────────────────┤
│ EXISTING SYSTEM (unchanged)                                 │
│                                                             │
│  ScenarioSimulator.tsx (renders ScenarioResult)             │
│  CascadeGraph.tsx (renders cascade from ScenarioResult)     │
│  AnalysisPanel.tsx (renders analysis from ScenarioResult)   │
│  ScenarioContext.tsx (stores ScenarioResult)                │
│  Home.tsx (deep-link navigation)                            │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**Rules that prevent scope creep:**
1. The diagram analyzer NEVER modifies existing types (`FactPattern`, `ScenarioResult`, `CellState`)
2. The diagram analyzer NEVER imports from `scrambler-evaluator.ts` (independent evaluation)
3. The diagram analyzer NEVER writes to the DOM outside its sidebar container
4. The pattern-evaluator produces a `ScenarioResult` that is indistinguishable from a scrambler-generated one
5. If a future feature requires changes to `ScenarioResult`, it must be proposed as a separate RFC

**What this prevents:**
- "Let's also add real-time monitoring" → Out of scope (no server)
- "Let's connect to Miro API directly" → Out of scope (requires OAuth, server-side)
- "Let's let users define custom patterns" → Out of scope (breaks schema integrity)
- "Let's add a pattern recommendation engine" → Out of scope (different feature)

**Confidence:** 0.9

## Summary: Architecture Position

The diagram analyzer is a **self-contained subsystem** with a single output type (`ScenarioResult`). It integrates with the existing system through the **same interface** as the scrambler — the renderer doesn't know or care about the source. Multiple patterns per diagram are supported via **union aggregation** (max weight per ASI). Evidence Explorer deep-links work **unchanged**. Onboarding extends with a **conditional Phase 6**. Scope creep is prevented by a **strict boundary contract** (only `ScenarioResult` crosses the line).
